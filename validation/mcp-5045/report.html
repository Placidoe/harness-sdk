STRANDS HARNESS SDK · ISSUE #5045

Cancel the waiter.
Keep the shared connection alive.

Technical solution and recorded local validation · 12 October 2026 (Asia/Shanghai)

Small lifetime fix · No public API change

What broke, and why this fixes it

The caller that starts an MCP connection can cancel its own wait. That does not cancel the underlying handshake. Previously, the caller's finally cleared the shared promise immediately, letting the next caller start a second connection on the same transport.

The patch clears that promise when the actual connection attempt settles, on success or failure. The identity guard remains in place so an older attempt cannot clear a newer one. The returned finally promise is still observed by the waiter or raceWithAbort; there is no detached rejection chain.

How the protocol check works

Actual network boundary

A real MCP server binds to a loopback HTTP port. The first request is held at a deterministic barrier. The creating caller aborts after that request arrives; a follower then joins before the barrier is released.

The real SDK connect method is spied on, not mocked. The test requires one invocation, then successfully lists and calls the server's echo tool.

Edge cases and scope

Both continueOnError=false and true are checked. A separate unit case checks a late connection rejection and explicit retry; that retry uses a mocked transport and does not establish recovery from every real transport failure.

Signal forwarding and tool metadata in #5043 are out of scope. General transport recreation after a failed handshake is also out of scope.
